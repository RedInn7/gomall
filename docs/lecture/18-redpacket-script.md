## 第 1 页　红包：Redis 分发与 DB 记账的一致性

*GOMALL · 第 18 讲*

这一讲讲红包。红包看着是个小功能，其实它同时是两件事：一件是高并发争抢，一件是真金白银的转账。我们用 Redis 管争抢，用 MySQL 管钱，今天所有的内容都围绕一个问题：这两边对不上的时候怎么办。先说红包这个功能本身是干什么的，再看为什么需要两套存储，然后看四张客诉单，一张一张把它们解决掉。

## 第 2 页　红包是拿来干什么的

*开场 · 业务背景*　（点 4 次）

在讲技术之前，先说清楚红包这个功能是拿来干什么的。它和微信群里的拼手气红包是一回事：一个用户从自己的钱包里拿出一笔钱，拆成若干份，发到群里让大家抢，先到先得，每人最多领一份，每份金额随机。在商城里，它是一种营销玩法，和优惠券、秒杀是同一类，用来拉人气、带活跃。整个过程四步：第一步发，填总金额、份数和祝福语，输支付密码，钱当场从钱包扣走。第二步分享，发包人拿到一个带口令的链接，发到群里。第三步抢，群友点开链接，抢到的钱直接进自己钱包。第四步过期，默认二十四小时，最长七天，没被领完的钱退回发包人。再看三条业务规则：单个红包最多两百块，每份至少一分钱，最多一千份；每人只能领一次，金额随机但总和必须等于总金额；最重要的一条，钱不能错，发出去多少，领走的加上退回的就必须是多少。今天后面所有的设计，都是为了在几百人同时抢的情况下守住这三条。

## 第 3 页　只用 MySQL：所有人排同一把锁

*00 · 核心认知*　（点 3 次）

先想最简单的做法：全放 MySQL。大年三十群里发个一百人的红包，几百人同一毫秒点开，所有请求抢的是同一行红包记录的行锁。拿到锁的那个人还要在锁里算随机金额、改余额、写流水，其他人只能排队。队一长，连接池耗尽，数据库就挂了。所以只用 MySQL 的问题是一个字：慢。

## 第 4 页　只用 Redis：扣了份额，钱不一定到账

*00 · 核心认知*　（点 3 次）

那全放 Redis 呢？快是够快了。但 Redis 不是账本，它没有跨表事务。份额扣掉了，正准备给钱包加钱，进程崩了，这笔钱就凭空消失，没有任何东西能把它回滚回来。所以只用 Redis 的问题是：它管不了钱。

## 第 5 页　铁律：Redis 发号码牌，MySQL 发钱

*00 · 核心认知*　（点 2 次）

所以 gomall 的分工是这样的：Redis 只负责发号码牌，决定谁拿到哪一份；MySQL 才负责真正发钱记账。请大家记住这条等式：红包总额，等于所有人落库领走的钱，加上过期退给发包人的钱。无论中间网络超时多少次、进程崩多少次、Redis 重启多少次，这条等式都必须成立，而且每一项都只从 MySQL 算，Redis 里剩多少我们不信。

## 第 6 页　全景：发红包、抢红包、后台兜底

*00 · 核心认知*　（点 2 次）

这张是全景图，现在不用记住每一步，只看三段。第一段发红包：先在内存里把金额拆好，再开事务扣钱，最后把拆好的金额推进 Redis。第二段抢红包：先在 Redis 里抢到一份，再开事务落库入账，失败了有一套回补逻辑。第三段是后台两个定时任务兜底。后面每一节讲的都是这里的一行，讲完再回来看就全通了。

## 第 7 页　先看四张客诉单：事故都出在两边的交界处

*一 · 四张客诉单*　（点 3 次）

红包上线以后，边界没处理好，客服会收到四类投诉。A：我点抢，提示失败，再点却说我领过了，钱没到。B：红包到期那一秒最后一份被抢走，结果抢的人拿到了钱，发包人也收到了这笔钱的退款，平台亏了。C：抢的时候转圈断开了，半小时过去，钱没到账，红包里也没有这一份了。D：发红包扣了我一百块，群里所有人点开都是已抢完。这四张单子有一个共同点：全都出在 Redis 和 MySQL 的交界处，一边做了，另一边没做。带着这四张单子往下听。

## 第 8 页　Redis 侧：两个 Key，抢包前后怎么变

*一 · 数据结构 · repository/cache/redpacket.go:16-22*　（点 4 次）

Redis 这边一场红包只有两个 key。第一个是 LIST，发包的时候把拆好的金额一次性推进去，抢就是从头上弹一个。第二个是 HASH，记谁抢了多少、什么时候抢的。看图：发包后 LIST 里三份，HASH 是空的；101 抢走三十块，LIST 剩两份，HASH 多一条。之后有两种走向：DB 失败了，就把三十块塞回 LIST、删掉标记；或者这一份成了孤儿，对账任务接手，在标记后面加一个冒号 r。这里有个问题：HASH 里为什么不只存个 1，而要存金额和时间？因为这三十块弹出来以后 LIST 里已经没有了，这时候断电，只有 HASH 还记得该给他补多少钱；时间是用来判断这笔领取是还在路上，还是已经卡死了。

## 第 9 页　MySQL 侧：两张核心表

*一 · 数据结构 · internal/redpacket/model.go:20-44*　（点 1 次）

MySQL 这边两张表。红包主表记总金额、总份数、剩余份数、过期时间和状态，状态只有三个：进行中、已抢完、已退款。领取表一个人领一次就是一行。注意领取表上的唯一索引，红包 ID 加用户 ID，这是数据库层面的最后一道保险，同一个人无论从哪条路进来，最多只能成功落一行。后面对账补领敢放心重试，靠的就是它。

## 第 10 页　ShareCode：自增 id 能遍历，口令不能

*一 · 1.2 防扫号口令*　（点 2 次）

红包 ID 是自增主键，一二三四往上涨。如果抢红包只要传 ID，写个循环脚本就能把全平台正在发的红包全抢光。所以发包时后端会生成一个十六位的随机十六进制口令，只在创建成功那一次响应里返回给发包人，由他拼进分享链接发给群友。没有口令的请求直接拒掉，返回八四零零六。

## 第 11 页　口令比较为什么不用 ==

*一 · 1.2 防扫号口令 · internal/redpacket/service.go:161-166*　（点 2 次）

再看代码里一个细节：口令比较没有用等号，用的是常量时间比较。因为等号是一个字节一个字节比的，第一位错了马上返回，前十五位都对才会比到第十六位，耗时不一样。攻击者量这个时间差，可以一位一位把口令猜出来，这叫计时攻击。常量时间比较不管对了几位都比到底，时间差就不泄露信息了。

## 第 12 页　金额什么时候定、放在哪：四种方案

*二 · 分发模型 · 方案取舍*　（点 4 次）

讲 gomall 的做法之前，先看看这个问题有几种解法。核心就两个问题：每一份的金额什么时候定，定好以后放在哪。方案 A，抢的时候实时算：只存剩余金额和剩余份数，每来一个人现算一份。好处是发包最轻，坏处是抢包这条最热的路上要读、要算、要写回，而且失败回补会把后面的分布搞乱。方案 B，发的时候一次拆好，只放进 Redis，这是 gomall 现在的做法：抢包只有一次 LPOP，回补就是原样塞回去。代价是这个金额数组没有落库，Redis 要是把它丢了，没法重建，只能提前退款。方案 C，发的时候拆好，并且每一份都在数据库里落一行，也就是发之前这个红包就已经完整设计好了。好处是 Redis 丢了可以从数据库重建，每一份都能审计，运营还可以指定某一份的金额；代价是发包事务要多写 N 行，领取的时候也要多更新一行。方案 D 是平台做活动的时候用的：活动开始前按预算把所有金额离线生成好，预热进缓存，开抢的时候只扣库存，预算一定不会超；但它要提前知道总量，不适合用户随手发的红包。从左到右看，金额定得越早就越可控，发包也越重。gomall 是用户之间随手发的小额红包，所以选了 B，把丢份额的风险交给后面要讲的池丢失提前退款来兜底。

## 第 13 页　发之前就设计好：每一份都先落库

*二 · 分发模型 · 方案 C（gomall 没有采用，用来对比）*　（点 5 次）

把方案 C 展开看一下，它和 gomall 现在的做法只差一步。发红包的时候，同一个事务里除了写主表、扣钱，还把拆好的每一份写进一张份额表：第一份三十块未领，第二份五十块未领，第三份二十块未领。然后推进 Redis 的不再是金额，而是份额编号。抢的时候 LPOP 拿到一个编号，再到数据库里把这一行改成已领，同时入账，在同一个事务里完成。这样做最大的好处是：Redis 要是把 LIST 丢了，不用退款，把数据库里还是未领的那几行重新推进去就行。另外每一份从生到死都有记录，对账更直接；运营想让某一份是大额，也可以在发之前直接指定。代价也很明显：一个一千份的红包，发包事务要多写一千行，领取的时候也要多更新一行。所以这是一个取舍：gomall 选择发包轻一点，丢了就退；如果是金额大、要审计、或者金额需要人为设计的红包，方案 C 更合适。

## 第 14 页　发包时预拆好，抢包只做一次 LPOP

*二 · 分发模型*　（点 4 次）

第二部分讲怎么分。核心就一句话：金额在发包的时候一次算完，抢包的时候只做一次 LPOP。发包是低频操作，慢一点没关系，所以拆金额、扣钱、推进 Redis 都在这里做。抢包是高并发热路径，这条路上没有随机数计算，没有分布式锁，就是从 LIST 头上弹一个数。有同学会问，为什么不在抢的时候用 Lua 实时算？因为那样脚本里要读剩余金额、读剩余份数、算随机数、再写回去，更麻烦的是 DB 失败要回补的时候，退回去的金额会把平均值搞乱。预拆以后，LIST 里就是一张张固定面额的代金券，抢是拿走一张，回补是原样放回一张，总额永远不会错。

## 第 15 页　算例：10 元（1000 分）拆成 3 份

*二 · 2.1 二倍均值 · repository/cache/redpacket.go:127-167*　（点 3 次）

金额怎么拆？最朴素的想法是在一到剩余总额之间随机，但这样第一个人可能直接拿走九十九块，后面的人只剩几分钱。gomall 用的是二倍均值法：每次随机的上限，是当前剩余人均金额的两倍。我们手算一遍，十块钱一千分拆三份。第一份：剩一千分三个人，人均三百三十三，两倍是六百六十六，所以在一到六百六十五之间随机，期望正好是人均。假设抽中三百。第二份：剩七百分两个人，人均三百五，两倍七百，在一到六百九十九之间随机，假设抽中五百。第三份不随机，直接拿走剩下的两百，这样总和一分不差。代码里还有一个保底：每一轮都要给后面没拆的每份至少留一分钱。最后为什么要洗牌？如果前两份运气不好都抽得很小，最后一份就特别大，不打乱的话大红包永远在最后一个位置。

## 第 16 页　去重、出队、打标记，一次原子完成

*二 · 2.2 抢包 Lua · repository/cache/redpacket.go:55-66*　（点 3 次）

抢包的脚本只有十行。第一步查 HASH，这个人领过没有，领过返回负二。第二步 LPOP，弹不出来说明抢完了，返回负一。第三步弹出来了，就在 HASH 里记一条，金额加当前时间，然后返回金额。重点是这三步写在一段 Lua 里，Redis 会把它当成一个整体原子执行，中间不会被别的命令插进来，所以不会出现两个人弹到同一份，也不会出现弹走了但没打上标记。右边是三次调用的结果：101 第一次抢到三十块；他再点一次，返回负二；等另外两份被抢走以后，104 再来就是负一。

## 第 17 页　钱先进红包托管，再分给领取人

*三 · 资金模型*　（点 3 次）

第三部分讲钱怎么走。发红包的时候，钱不是直接打给谁，因为这时候还不知道谁会抢到。钱先从发包人钱包扣出来，进一个系统托管账户。有人抢到一份，就从托管账户转一份到他钱包。过期没领完的，再从托管账户退回发包人。看这个例子：A 发一百块，红包 ID 是八十八，托管里有一万分；B 领三十，剩七千；C 领五十，剩两千；二十四小时后过期，退二十给 A，托管归零。托管账户最后必须是零，多一分少一分都说明出事了。每个箭头是一组一借一贷的复式分录，发包、领包、退款三段各自独立幂等。

## 第 18 页　account_transaction 里的 8 条流水

*三 · 3.1 完整台账*　（点 1 次）

上一页的四个箭头，落到流水表里就是这八行，每个箭头两行，一借一贷。大家重点看第三列 ref_order_id：发包和退款这四行填的是红包 ID 八十八，领包这四行填的是领取记录的 ID，五百零一和五百零二。为什么不一样，下一页讲。最下面算一下托管账户：进一万，出三千、五千、两千，净额是零，一分不多一分不少。

## 第 19 页　领包的 ref_order_id 为什么用“领取记录 ID”

*三 · 3.2 防重唯一索引*　（点 3 次）

流水表靠一个唯一索引防重复记账，三列：关联单号、方向、业务类型。注意里面没有用户 ID。发包和退款，一个红包只会发一次、最多退一次，用红包 ID 做单号没问题。但领包是多个人领同一个红包，如果也用红包 ID，B 领完写了一行八十八、入账、领包，C 再来写的还是八十八、入账、领包，直接撞唯一索引。所以领包用的是每个人自己那条领取记录的 ID，五百零一、五百零二，互不冲突。

## 第 20 页　永远先改用户钱包，后记系统托管

*三 · 3.3 记账顺序 · internal/redpacket/settle.go:101-110*　（点 2 次）

每个结算函数都是两条腿，而且顺序固定：先改用户钱包，再记托管账户。原因有两个。第一，先难后易。用户钱包这条腿要加行锁、解密余额、检查够不够扣，是最容易失败的；它失败了直接返回，托管那边根本不用碰。第二，幂等。如果这是一次重复调用，第一条腿会发现流水已经存在，返回 skipped，整个函数直接结束，两条腿一起跳过，不会只记一半。

## 第 21 页　Redis 先扣， DB 说了算

*四 · 一致性边界*

第四部分是这一讲的核心。先定一个认知：Redis 里 LPOP 成功，只代表你拿到了一张号码牌，钱有没有进钱包，由后面那个 DB 事务决定。一旦 DB 报错，绝不能盲目把份额塞回 Redis，必须先查库确认，再对比标记回补。接下来几页就是把这句话拆开讲。

## 第 22 页　一次抢包：先 Redis 抢份额，再 DB 落库入账

*四 · 4.1 领取主链路*　（点 4 次）

这张图是一次完整的抢包。前半段很顺：校验口令和状态，Redis 抢一份，抢不到就直接返回已抢完或者已领过。抢到了，DB 事务落库入账，成功返回。要注意的是最后一行，DB 事务报错以后怎么办。它没有直接回补 Redis，而是先去数据库查了一次，然后分成四种情况处理。为什么要这么麻烦，看下一页。

## 第 23 页　很多人会这样写：报错就把份额塞回 Redis

*四 · 4.2 DB 报错之后*　（点 1 次）

很多同学会这么写：Redis 抢到了，DB 报错了，那就把份额塞回 Redis。看着很对称，其实很危险。问题在于：报错不等于没提交。事务在 MySQL 里可能已经提交成功，钱已经进了钱包，只是 MySQL 回确认包的路上网络闪断了，Go 进程收到的是一个连接错误。这时候无脑回补会发生什么，看下一页。

## 第 24 页　一份 30 元被发了两次

*四 · 4.2 无脑回补*　（点 5 次）

看图。A 抢到三十块，DB 事务在 MySQL 里其实已经提交成功，钱已经进了 A 的钱包，但回确认包的路上网络断了，服务收到的是一个连接错误。这时候无脑回补，把三十块塞回 LIST。下一个人 B 来了，又把这三十块抢走并且入账。同一份三十块发了两次，托管账户被多扣了三十。

## 第 25 页　正确做法：先反查 GetClaim，再分四种情况

*四 · 4.2 四分支判定 · internal/redpacket/service.go:213-238*　（点 5 次）

gomall 的做法是：DB 报错以后，先去数据库反查这条领取记录，再分四种情况。第一，连反查都报错，数据库彻底连不上了，这时候什么都不知道，就什么都不动，标记留在 Redis 里，交给后台对账。第二，库里查到了记录，说明刚才是假失败，直接按成功返回。第三，事务报的是红包已结束，说明剩下的钱已经退给发包人了，这一份不能再放回去给别人抢。第四，确认库里没有、红包还在进行中，这时候才回补。大家记一个结论：四个分支里只有一个会回补。分支四后面还有个小尾巴，回补的时候发现对账任务已经接手了，就再查一次库，这个放到第五部分讲。

## 第 26 页　抢最后一份撞上过期退款：领取事务先拿到行锁

*四 · 4.3 工单 B · 情况一*　（点 4 次）

现在解决工单 B。一百块的红包十二点整到期，还剩最后一份二十块。就在十二点整这一毫秒，用户 C 抢到了这二十块，正在落库；同时过期回收任务也扫到了这个红包，准备把没领完的钱退给发包人。两边怎么不撞车？靠红包主表这一行的行锁。先看领取事务先到的情况：它执行扣减剩余份数的 UPDATE，拿到行锁。退款事务的第一句是 SELECT FOR UPDATE，要的是同一把锁，只能等。等领取事务提交了，退款事务拿到锁，读到状态已经是已抢完，直接退出，一分钱不退。

## 第 27 页　反过来：退款事务先拿到行锁

*四 · 4.3 工单 B · 情况二 · internal/redpacket/task.go:59-105*　（点 4 次）

反过来，退款事务先拿到锁。它把已领金额加总，算出该退多少，把状态改成已退款，提交。这时候领取事务的 UPDATE 才轮到执行，但这条 UPDATE 带着条件：剩余份数大于零，而且状态必须是进行中。现在状态已经是已退款，影响零行，代码看到零行就抛红包已结束，整个领取事务回滚，包括前面那条 INSERT。回到上层，正好落进四分支里的分支三，不回补。所以不管谁先谁后，两个事务都是排着队来的，这二十块要么给 C，要么退给发包人，不会两边都给。

## 第 28 页　为什么 FOR UPDATE 必须是事务第一条语句

*四 · 4.4 MVCC 快照时机*　（点 2 次）

退款事务的代码里有一句很严厉的注释：加锁读必须是事务的第一条语句，前面不能插任何普通查询。为什么？这是 MySQL 可重复读隔离级别的机制。事务里第一条普通 SELECT 执行的那一刻，数据库给这个事务拍一张快照，之后所有普通读看到的都是这张快照，包括后面那条求和。而加锁读不拍快照，它等锁，读最新数据。如果有人在加锁读前面手滑加了一句普通查询，会发生什么？看下一页。

## 第 29 页　首行多了一句普通 SELECT：多退 50 元

*四 · 4.4 反面推演*　（点 5 次）

看图：红包八十八，一百块三份，B 已经领了三十。到期那一瞬间，C 抢到了五十，还剩一份，状态仍然是进行中。第一步，退款事务先做了一次普通读，快照拍下来了，这时候已领三十。第二步，C 的领取事务提交，真实已领变成八十。第三步加锁读，读到的是最新的行，状态还是进行中，继续往下。第四步求和，这是普通读，用的是第一步那张旧快照，看不到 C 的五十，算出来还是三十。第五步，一百减三十，退七十。结果一百块的红包，领走八十，又退了七十，多退了五十。

## 第 30 页　加锁读在前：快照在拿到锁之后才建

*四 · 4.4 正确顺序*　（点 4 次）

正确的顺序是这样：加锁读放在第一句。它不拍快照，只是排队等锁。等它拿到锁，说明排在前面的领取事务都已经提交了。这时候再执行求和，这才是事务里第一条普通读，快照是现在才拍的，C 的五十块看得见，算出来已领八十，退二十，对了。同样两条 SQL，只是先后顺序不同，结果差了五十块钱。这就是那条注释存在的原因。

## 第 31 页　回补 Lua：先看标记，再决定放不放回

*四 · 4.5 工单 A · repository/cache/redpacket.go:92-99*　（点 3 次）

现在回到工单 A：点抢失败，再点提示已领过。原因是 DB 失败以后，Redis 里的已领标记没删。解决它的就是这段回补脚本，分支四调的就是它。它先读这个用户的标记，分三种情况。标记不在了，说明已经回补过，直接返回，这是幂等。标记末尾有冒号 r，说明后台对账已经接手这一份，绝不放回。只有普通标记才真正回补：把金额塞回 LIST，再把标记删掉。删掉标记这一步，就是工单 A 的解药，用户再点一次就能重新抢。

## 第 32 页　请求死掉以后，靠后台三道防线收尾

*五 · 三道兜底防线*　（点 3 次）

前面讲的都是请求还活着的时候怎么处理。但请求可能直接死掉，比如服务器断电。所以第五部分是三道后台防线。先看状态机，很简单：红包从进行中出发，只有两个终点，抢完了，或者退款了。退款有三个来源：过期、份额池丢失、发包时 Redis 写入失败。下面三道防线，分别对应工单 C、工单 D，还有正常的过期。

## 第 33 页　孤儿领取：份额卡在半空，靠标记补发

*五 · 5.2 工单 C · internal/redpacket/task.go:179-211*　（点 1 次）

工单 C：抢到了，钱没到账。什么情况会这样？Redis 抢成功了，LIST 里少了一份，HASH 里记了他的名字，然后服务器断电，或者 DB 事务超时而且回补也失败了。这时候三十块不在 LIST 里，也不在数据库里，卡在半空，我们叫它孤儿领取。唯一的线索就是 HASH 里那条标记，上面有金额和时间。对账任务每两分钟跑一次，把每条标记和数据库比。库里有，正常，跳过。库里没有，但抢到还不到一分钟，可能 DB 事务还在跑，先不动。超过一分钟还没落库，就是孤儿：先把标记改成带冒号 r 的，抢占成功以后，替用户调同一个领取事务，把钱补给他。注意是补给抢到的人，不是退给发包人，因为这一份确实是他抢到的。

## 第 34 页　对账先到：慢请求的回补被拒，按成功返回

*五 · 5.2 :r 锁互斥（一）*　（点 4 次）

这里有个并发问题。原来那个请求其实没死，只是卡了一分多钟，现在醒过来要回补；同一时刻对账也盯上了这条标记要补领。一个要把钱放回 Redis，一个要把钱发给用户，两个都做了就又多发一份。冒号 r 就是用来让它们二选一的。先看对账先到：对账把标记改成带冒号 r 的，然后落库发钱。慢请求醒来执行回补，脚本一看标记末尾是冒号 r，拒绝放回，返回负一，也就是 ErrRedPacketClaimRepairing。慢请求收到这个返回值，再去查一次库，发现对账已经帮他把钱发了，于是直接告诉用户：抢包成功。这就是四分支里分支四的那个小尾巴。

## 第 35 页　回补先到：对账抢占失败，跳过这一份

*五 · 5.2 :r 锁互斥（二）*　（点 4 次）

再看回补先到。对账先读到了这条标记，还没来得及加锁，慢请求的回补脚本先执行了：金额放回 LIST，标记删掉。对账接着去加锁，加锁脚本要求标记的值和刚才读到的一模一样，现在标记已经没了，对不上，返回零。对账就跳过这一份，不去发钱。所以规则很简单：两段脚本都是先看标记再动手，谁先改到标记，这一份就归谁处理，另一个让路。

## 第 36 页　份额池丢失：amounts 这个 LIST 不存在了

*五 · 5.3 工单 D*　（点 2 次）

工单 D：发包扣了钱，但没人能抢。原因是扣款事务提交了，往 Redis 推金额的时候 Redis 挂了，或者运行中途 Redis 数据丢了，那个 LIST 根本不存在，别人一点开就是已抢完。这里有两道防线。第一道在发包接口里：写 Redis 失败的那一刻，当场把钱全额退回发包人，状态置为已退款。第二道在对账任务里：如果红包创建超过一分钟，LIST 不存在，没有在途的标记，数据库里却还有剩余份数，那就说明份额池丢了，没人能再抢到，直接提前退款，不用让发包人等七天过期。

## 第 37 页　先 EXISTS，后读 claimed：正常抢完不会误退

*五 · 5.3 池丢失检查 · 正确顺序*　（点 4 次）

判断份额池丢没丢，有一个坑。LIST 不存在有两种可能：一种是真丢了，一种是最后一份刚被正常抢走，因为 Redis 会自动删掉空的 LIST。怎么区分？靠检查顺序：必须先查 LIST 在不在，再读 HASH 里的标记。看图，用户 Z 抢走最后一份，LIST 消失。对账查 LIST，不存在。然后读标记，因为抢包脚本里 LPOP 和打标记是原子的，只要 LIST 是被抢空的，Z 的标记这时候一定已经在 HASH 里了，而且是刚刚打上的，不到一分钟。对账看到有在途标记，就知道这是正常抢完，不退款。

## 第 38 页　先读 claimed，后 EXISTS：把抢到的钱退给了发包人

*五 · 5.3 池丢失检查 · 错误顺序*　（点 4 次）

如果顺序反过来，先读标记再查 LIST。对账读标记的时候，最后一份还没人抢，没有 Z。就在这之后的一瞬间，Z 抢走了最后一份，LIST 消失。对账接着查 LIST，不存在。它手里的信息是：没有在途标记，LIST 没了，数据库里红包还是进行中、还剩一份，于是误判成份额池丢失，调 refundRedPacketLeft 把这二十块退给了发包人。等 Z 的领取事务跑到扣减那一步，红包已经是已退款，被拒掉。Z 明明抢到了，钱却退给了发包人。两次读取调个顺序，结论就完全不一样。

## 第 39 页　先补齐孤儿，再按 DB 退剩余

*五 · 5.4 过期回收 · internal/redpacket/task.go:32-50*　（点 3 次）

最后一道防线，过期回收，每五分钟一次。它对每个过期的红包做两步，顺序不能反。第一步，先跑一遍对账，把孤儿补给领取人。第二步，再按数据库算，总额减去已领总和，退给发包人。为什么必须先补孤儿？因为一旦退款，状态就变成已退款，那个抢到了却卡在半空的用户，他的领取事务会被拒，这份钱就再也补不给他了。还有一个细节：如果对账出错，或者还有在途的标记没下结论，这一轮先不退，最多等一小时；一小时还没结果，保底退给发包人，钱至少不会丢。如果对账里已经因为池丢失提前退过款，这里也直接跳过。

## 第 46 页　两边对不上的时候， 永远听 MySQL 的

*本讲小结*
