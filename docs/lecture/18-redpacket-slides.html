这一讲讲红包。红包看着是个小功能，其实它同时是两件事：一件是高并发争抢，一件是真金白银的转账。我们用 Redis 管争抢，用 MySQL 管钱，今天所有的内容都围绕一个问题：这两边对不上的时候怎么办。先说红包这个功能本身是干什么的，再看为什么需要两套存储，然后看四张客诉单，一张一张把它们解决掉。

在讲技术之前，先说清楚红包这个功能是拿来干什么的。它和微信群里的拼手气红包是一回事：一个用户从自己的钱包里拿出一笔钱，拆成若干份，发到群里让大家抢，先到先得，每人最多领一份，每份金额随机。在商城里，它是一种营销玩法，和优惠券、秒杀是同一类，用来拉人气、带活跃。整个过程四步：第一步发，填总金额、份数和祝福语，输支付密码，钱当场从钱包扣走。第二步分享，发包人拿到一个带口令的链接，发到群里。第三步抢，群友点开链接，抢到的钱直接进自己钱包。第四步过期，默认二十四小时，最长七天，没被领完的钱退回发包人。再看三条业务规则：单个红包最多两百块，每份至少一分钱，最多一千份；每人只能领一次，金额随机但总和必须等于总金额；最重要的一条，钱不能错，发出去多少，领走的加上退回的就必须是多少。今天后面所有的设计，都是为了在几百人同时抢的情况下守住这三条。

攻击者测微秒级时间差，一位一位猜出口令：计时攻击。

再看代码里一个细节：口令比较没有用等号，用的是常量时间比较。因为等号是一个字节一个字节比的，第一位错了马上返回，前十五位都对才会比到第十六位，耗时不一样。攻击者量这个时间差，可以一位一位把口令猜出来，这叫计时攻击。常量时间比较不管对了几位都比到底，时间差就不泄露信息了。

二 · 分发模型 · 方案取舍

金额什么时候定、放在哪：四种方案

方案 A

抢的时候实时算

只存剩余金额和剩余份数，每次抢都现算一份。

省：发包最轻，不占额外存储。

费：热路径要读、算、写回；失败回补会改变后面的分布。

方案 B · gomall 现在用的

发时预拆，只放 Redis

金额数组一次算好，RPUSH 进 LIST。

省：抢包只有一次 LPOP，回补原样塞回。

费：数组不落库，Redis 丢了没法重建，只能提前退款。

方案 C

发时预拆，逐份落库

发之前每一份就定好，DB 里一份一行。

省：Redis 丢了能从 DB 重建；每份可审计、可指定金额。

费：发包事务多写 N 行，领取多更新一行。

方案 D

活动前批量预生成

平台按预算离线生成全部金额，开抢前预热进缓存。

省：开抢时只扣库存，预算不会超。

费：要提前知道总量，不适合用户随手发。

越往右，金额定得越早、越可控，发包也越重。gomall 是用户随手发的小额红包，选 B：把丢份额的风险交给“池丢失提前退款”兜底。

讲 gomall 的做法之前，先看看这个问题有几种解法。核心就两个问题：每一份的金额什么时候定，定好以后放在哪。方案 A，抢的时候实时算：只存剩余金额和剩余份数，每来一个人现算一份。好处是发包最轻，坏处是抢包这条最热的路上要读、要算、要写回，而且失败回补会把后面的分布搞乱。方案 B，发的时候一次拆好，只放进 Redis，这是 gomall 现在的做法：抢包只有一次 LPOP，回补就是原样塞回去。代价是这个金额数组没有落库，Redis 要是把它丢了，没法重建，只能提前退款。方案 C，发的时候拆好，并且每一份都在数据库里落一行，也就是发之前这个红包就已经完整设计好了。好处是 Redis 丢了可以从数据库重建，每一份都能审计，运营还可以指定某一份的金额；代价是发包事务要多写 N 行，领取的时候也要多更新一行。方案 D 是平台做活动的时候用的：活动开始前按预算把所有金额离线生成好，预热进缓存，开抢的时候只扣库存，预算一定不会超；但它要提前知道总量，不适合用户随手发的红包。从左到右看，金额定得越早就越可控，发包也越重。gomall 是用户之间随手发的小额红包，所以选了 B，把丢份额的风险交给后面要讲的池丢失提前退款来兜底。

把方案 C 展开看一下，它和 gomall 现在的做法只差一步。发红包的时候，同一个事务里除了写主表、扣钱，还把拆好的每一份写进一张份额表：第一份三十块未领，第二份五十块未领，第三份二十块未领。然后推进 Redis 的不再是金额，而是份额编号。抢的时候 LPOP 拿到一个编号，再到数据库里把这一行改成已领，同时入账，在同一个事务里完成。这样做最大的好处是：Redis 要是把 LIST 丢了，不用退款，把数据库里还是未领的那几行重新推进去就行。另外每一份从生到死都有记录，对账更直接；运营想让某一份是大额，也可以在发之前直接指定。代价也很明显：一个一千份的红包，发包事务要多写一千行，领取的时候也要多更新一行。所以这是一个取舍：gomall 选择发包轻一点，丢了就退；如果是金额大、要审计、或者金额需要人为设计的红包，方案 C 更合适。

第二部分讲怎么分。核心就一句话：金额在发包的时候一次算完，抢包的时候只做一次 LPOP。发包是低频操作，慢一点没关系，所以拆金额、扣钱、推进 Redis 都在这里做。抢包是高并发热路径，这条路上没有随机数计算，没有分布式锁，就是从 LIST 头上弹一个数。有同学会问，为什么不在抢的时候用 Lua 实时算？因为那样脚本里要读剩余金额、读剩余份数、算随机数、再写回去，更麻烦的是 DB 失败要回补的时候，退回去的金额会把平均值搞乱。预拆以后，LIST 里就是一张张固定面额的代金券，抢是拿走一张，回补是原样放回一张，总额永远不会错。

金额怎么拆？最朴素的想法是在一到剩余总额之间随机，但这样第一个人可能直接拿走九十九块，后面的人只剩几分钱。gomall 用的是二倍均值法：每次随机的上限，是当前剩余人均金额的两倍。我们手算一遍，十块钱一千分拆三份。第一份：剩一千分三个人，人均三百三十三，两倍是六百六十六，所以在一到六百六十五之间随机，期望正好是人均。假设抽中三百。第二份：剩七百分两个人，人均三百五，两倍七百，在一到六百九十九之间随机，假设抽中五百。第三份不随机，直接拿走剩下的两百，这样总和一分不差。代码里还有一个保底：每一轮都要给后面没拆的每份至少留一分钱。最后为什么要洗牌？如果前两份运气不好都抽得很小，最后一份就特别大，不打乱的话大红包永远在最后一个位置。

先难后易

钱包一侧要加行锁、解密余额、校验够不够扣，最容易失败。余额不够直接返回，托管表不用碰。

幂等短路

重复调用时台账已存在，adjustWallet 返回 skipped = true，两条腿一起跳过。

每个结算函数都是两条腿，而且顺序固定：先改用户钱包，再记托管账户。原因有两个。第一，先难后易。用户钱包这条腿要加行锁、解密余额、检查够不够扣，是最容易失败的；它失败了直接返回，托管那边根本不用碰。第二，幂等。如果这是一次重复调用，第一条腿会发现流水已经存在，返回 skipped，整个函数直接结束，两条腿一起跳过，不会只记一半。

gomall 的做法是：DB 报错以后，先去数据库反查这条领取记录，再分四种情况。第一，连反查都报错，数据库彻底连不上了，这时候什么都不知道，就什么都不动，标记留在 Redis 里，交给后台对账。第二，库里查到了记录，说明刚才是假失败，直接按成功返回。第三，事务报的是红包已结束，说明剩下的钱已经退给发包人了，这一份不能再放回去给别人抢。第四，确认库里没有、红包还在进行中，这时候才回补。大家记一个结论：四个分支里只有一个会回补。分支四后面还有个小尾巴，回补的时候发现对账任务已经接手了，就再查一次库，这个放到第五部分讲。

四 · 4.4 MVCC 快照时机

为什么 FOR UPDATE 必须是事务第一条语句

MySQL InnoDB 默认 RR（可重复读）隔离级别下，两种读的行为不一样：

普通 SELECT（不加锁）

事务里第一条普通读执行的瞬间，建立 ReadView 快照。

此后所有普通读（包括 SUM）只看得到快照时刻的数据。

SELECT ... FOR UPDATE（加锁读）

不建立快照。

等行锁，读最新已提交的数据。

GetForUpdate 前面不能插任何普通 SELECT：否则快照提前建立，后面的 SUM 看不到并发提交的领取

退款事务的代码里有一句很严厉的注释：加锁读必须是事务的第一条语句，前面不能插任何普通查询。为什么？这是 MySQL 可重复读隔离级别的机制。事务里第一条普通 SELECT 执行的那一刻，数据库给这个事务拍一张快照，之后所有普通读看到的都是这张快照，包括后面那条求和。而加锁读不拍快照，它等锁，读最新数据。如果有人在加锁读前面手滑加了一句普通查询，会发生什么？看下一页。

正确的顺序是这样：加锁读放在第一句。它不拍快照，只是排队等锁。等它拿到锁，说明排在前面的领取事务都已经提交了。这时候再执行求和，这才是事务里第一条普通读，快照是现在才拍的，C 的五十块看得见，算出来已领八十，退二十，对了。同样两条 SQL，只是先后顺序不同，结果差了五十块钱。这就是那条注释存在的原因。

现在回到工单 A：点抢失败，再点提示已领过。原因是 DB 失败以后，Redis 里的已领标记没删。解决它的就是这段回补脚本，分支四调的就是它。它先读这个用户的标记，分三种情况。标记不在了，说明已经回补过，直接返回，这是幂等。标记末尾有冒号 r，说明后台对账已经接手这一份，绝不放回。只有普通标记才真正回补：把金额塞回 LIST，再把标记删掉。删掉标记这一步，就是工单 A 的解药，用户再点一次就能重新抢。

工单 C：抢到了，钱没到账。什么情况会这样？Redis 抢成功了，LIST 里少了一份，HASH 里记了他的名字，然后服务器断电，或者 DB 事务超时而且回补也失败了。这时候三十块不在 LIST 里，也不在数据库里，卡在半空，我们叫它孤儿领取。唯一的线索就是 HASH 里那条标记，上面有金额和时间。对账任务每两分钟跑一次，把每条标记和数据库比。库里有，正常，跳过。库里没有，但抢到还不到一分钟，可能 DB 事务还在跑，先不动。超过一分钟还没落库，就是孤儿：先把标记改成带冒号 r 的，抢占成功以后，替用户调同一个领取事务，把钱补给他。注意是补给抢到的人，不是退给发包人，因为这一份确实是他抢到的。

本讲小结

两边对不上的时候，
永远听 MySQL 的

Redis 决定谁拿到哪一份，MySQL 决定钱有没有动

A 先查库再回补 · B FOR UPDATE 放事务首行 · C 孤儿对账补领 · D 立即退款 + 池丢失检测

最后用一句话收尾：Redis 决定谁拿到哪一份，MySQL 决定钱有没有动，两边对不上的时候，永远听 MySQL 的。四张客诉单对应四个机制：A 靠先查库、再比较标记回补；B 靠把加锁读放在事务第一句，让领取和退款串行；C 靠孤儿对账补领；D 靠发包失败立即退款，加上份额池丢失检测。
