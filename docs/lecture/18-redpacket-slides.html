开场 · 业务背景

红包是拿来干什么的

用户从自己的钱包里拿出一笔钱，拆成若干份，发给一群人先到先得：每人最多领一份，金额随机，没领完的到期退回。它是商城里的一种营销玩法，和优惠券、秒杀同一类。

① 发
金额、份数、祝福语
验支付密码后当场扣款

② 分享
拿到带口令的链接
发到群里

③ 抢
群友点开，先到先得
钱直接进自己钱包

④ 过期
默认 24 小时，最长 7 天
没领完的退回发包人

金额

单个红包最多 200 元，每份至少 1 分，最多 1000 份。

公平

每人只能领一次；每份金额随机，但总和必须等于总金额。

钱不能错

发出去多少，领走的加退回的就必须是多少，一分不多一分不少。

只为了防重复领，名单上写个 1 就够了。实际写的是 金额:抢到的时间，例如 3000:1730680000。

如果只写

记金额

知道补多少

那 30 元已经从一摞里拿走，数据库里也没有。名单是唯一还记得这个数的地方。

记时间

分清在途和卡死

ShareCode 是红包的领取口令：只有拿到分享链接的人才能抢这个红包，相当于微信里“只有群里的人能抢”。

口令比较为什么不用 ==

func codeMatches(rp *RedPacket, code string, legacyOK bool) bool {

if rp.ShareCode == "" {

return legacyOK // 没有口令的老红包

}

return subtle.ConstantTimeCompare([]byte(rp.ShareCode), []byte(code)) == 1

}

普通 == 逐字节比较

第 1 位错就立刻返回；前 15 位都对才比第 16 位。

攻击者测微秒级时间差，一位一位猜出口令：计时攻击。

ConstantTimeCompare

不管对了几位，永远比完所有字节。

耗时恒定，时间差不泄露信息。

二 · 分发模型 · 方案取舍

金额什么时候定、放在哪：四种方案

方案 A

抢的时候实时算

只存剩余金额和剩余份数，每次抢都现算一份。

省：发包最轻，不占额外存储。

费：热路径要读、算、写回；失败回补会改变后面的分布。

方案 B · gomall 现在用的

发时预拆，只放 Redis

金额数组一次算好，RPUSH 进 LIST。

省：抢包只有一次 LPOP，回补原样塞回。

费：数组不落库，Redis 丢了没法重建，只能提前退款。

方案 C

发时预拆，逐份落库

发之前每一份就定好，DB 里一份一行。

省：Redis 丢了能从 DB 重建；每份可审计、可指定金额。

费：发包事务多写 N 行，领取多更新一行。

方案 D

活动前批量预生成

平台按预算离线生成全部金额，开抢前预热进缓存。

省：开抢时只扣库存，预算不会超。

费：要提前知道总量，不适合用户随手发。

越往右，金额定得越早、越可控，发包也越重。gomall 是用户随手发的小额红包，选 B：把丢份额的风险交给“池丢失提前退款”兜底。

四 · 4.2 DB 报错之后

DB 报错了，先查库确认

报错 ≠ 没提交

可能一

事务真的没提交

钱没动。

这一份应该放回 Redis，让别人继续抢。

可能二

MySQL 里已经 COMMIT

钱已进用户钱包，只是确认包在路上丢了，Go 进程收到 driver: bad connection。

这一份不能放回，放回就会被第二个人领走。

两种情况服务端拿到的都只是一个 error，光看报错分不清。所以先用 GetClaim 反查：库里有记录就是已到账，没有才考虑放回。

四 · 4.2 四分支判定 · internal/redpacket/service.go:217-246

先反查 GetClaim，再分四种情况

分支 1 · qErr != nil

连反查都报错

什么都不知道，就什么都不动。

不回补，保留 claimed 标记，交给对账兜底。

分支 2 · existing != nil

库里已有记录

假失败：COMMIT 成功但回包丢了。

不回补，按成功返回库里的金额。

分支 3 · errRedPacketClosed

红包已结束

剩余的钱已按 DB 退给发包人。

不回补，这份不能再给别人抢。

分支 4 · default

确认没落库

红包还在进行中。

执行回补 Lua：LPUSH 放回 + HDEL 删标记。

四个分支里只有分支 4 会回补。回补若返回 ErrRedPacketClaimRepairing（对账已接手），再查一次 GetClaim，落库了就按成功返回。
